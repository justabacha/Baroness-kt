## Summary

The Wishlist sync feature is **architecturally sound** with proper offline-first design, Room caching, WorkManager scheduling, and Supabase realtime integration. However, there are **5 critical issues** blocking notifications and creating UX problems:

1. **POST_NOTIFICATIONS permission never requested** — Runtime permission missing for Android 13+ (critical)
2. **Notification channels never initialized** — `createNotificationChannels()` not called (critical)
3. **Race conditions in WorkManager enqueueing** — Multiple simultaneous operations create duplicate sync jobs (critical)
4. **Realtime notifications race condition** — NotificationViewModel may not be injected before realtime events fire (critical)
5. **SyncQueue operation mismatch** — Reactions/ratings use "upsert" operation but SyncManager might not handle correctly (medium)

**Identity handling is correct** — creatorId properly uses "phesty_official" and "baroness_official" format throughout the codebase.

**Data flow is correct** — Wishes are properly queued for sync and the SyncManager correctly processes them.

### Issue #1: POST_NOTIFICATIONS Permission Not Requested at Runtime
- **Files:** `app/src/main/java/com/baroness/app/MainActivity.kt`, `app/src/main/AndroidManifest.xml`
- **Problem:** The `POST_NOTIFICATIONS` permission is declared in AndroidManifest.xml (line 28) but **never requested at runtime**. On Android 13+ (API level 33+), apps must explicitly request this permission using `ActivityCompat.requestPermissions()` or similar. Without this, system notifications will silently fail.
- **Severity:** 🔴 Critical
- **Current State:**
  - ✅ Permission declared in AndroidManifest.xml:28
  - ❌ No runtime permission request in MainActivity
  - ❌ No permission check before showing notifications
- **Suggested Fix:** Add permission request in MainActivity.onCreate():
  ```kotlin
  if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {  // Android 13+
      if (ActivityCompat.checkSelfPermission(this, 
          Manifest.permission.POST_NOTIFICATIONS) != PackageManager.PERMISSION_GRANTED) {
          ActivityCompat.requestPermissions(this,
              arrayOf(Manifest.permission.POST_NOTIFICATIONS), 
              NOTIFICATION_PERMISSION_REQUEST_CODE)
      }
  }
  ```
- **Behavior Impact:** Major - All push notifications will fail silently on Android 13+
- **Offline Impact:** N/A - This affects system notifications, not offline sync

### Issue #3: Potential Race Condition - Multiple WorkManager Jobs Enqueued Simultaneously
- **Files:** `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt` (lines 456, 465, 476, 488, 500), `app/src/main/java/com/baroness/app/workers/SyncWorker.kt`
- **Problem:** Every CRUD operation on wishes calls `syncNow()`, which enqueues a **separate OneTimeWorkRequest**. If a user rapidly creates multiple wishes, modifies them, or reacts, multiple work requests are queued with identical constraints. This can cause:
  - Duplicate sync jobs running in parallel
  - Race conditions when updating sync status
  - Potential ID swap collisions in the temp ID → server ID mapping (SyncManager line 114-122)
- **Severity:** 🔴 Critical
- **Current State:**
  ```kotlin
  // Line 456: insertWish calls syncNow()
  syncManager.queueItem(...)
  syncNow()  // Enqueues a new OneTimeWorkRequest
  
  // Line 465: deleteWish calls syncNow()
  syncManager.queueItem(...)
  syncNow()  // Another new OneTimeWorkRequest!
  
  // Line 476: updateWishStatus calls syncNow()
  syncNow()  // Another new OneTimeWorkRequest!
  ```
- **Evidence:**
  - WishlistRepository lines 447-457: Insert queues then calls syncNow()
  - Lines 459-466: Delete queues then calls syncNow()
  - Lines 468-477: Status update queues then calls syncNow()
  - Lines 479-489: Reaction queues then calls syncNow()
  - Lines 491-501: Rating queues then calls syncNow()
  
  Each `syncNow()` call creates a **new** OneTimeWorkRequest instead of reusing/consolidating work.

- **Suggested Fix:** Use `enqueueUniqueWork()` instead of `enqueue()` to ensure only one sync job is active:
  ```kotlin
  suspend fun syncNow() {
      val workRequest = OneTimeWorkRequestBuilder<SyncWorker>()
          .setConstraints(...)
          .build()
      workManager.enqueueUniqueWork(
          "wishlist_sync",  // Unique name
          ExistingWorkPolicy.REPLACE,  // Replace if already queued
          workRequest
      )
  }
  ```
- **Behavior Impact:** Major - Can cause lost updates, duplicate syncs, ID collision errors
- **Offline Impact:** Yes - Could corrupt sync queue when restoring from offline

- **Severity:** 🔴 Critical
- **Current State:**

  // Line 281-295: Realtime handler tries to use it

  ```

  2. WishlistScreen loads (creates WishlistViewModel line 32)
  3. WishlistViewModel init block creates repository (line 17)
  4. Repository init block calls subscribeToRealtime() (line 82)
  5. Realtime channel subscribes and starts listening
  6. **Meanwhile**, MainActivity.onCreate() loads

- **Offline Impact:** Yes - First notification after app launch will be missed

### Issue #9: Missing Error Recovery for Failed ID Swaps

      }

  ```
- **Severity:** 🟡 Medium
- **Suggested Fix:** Add recovery for failed deletions:

## Architecture Recommendations

### 1. Implement Unique Work Scheduling Pattern
The current WorkManager pattern uses separate enqueue calls for every operation. Implement a pattern where:
- Use `enqueueUniqueWork()` instead of `enqueue()`
- Consolidate all sync operations into a single queued job
- Add exponential backoff for network failures
- Add max retry limits with user notification

### 2. Inject Dependencies at Repository Creation Time
Rather than lazy-setting the NotificationViewModel, pass it to the Repository constructor:
```kotlin
class WishlistRepository private constructor(
    context: Context,
    private val notificationViewModel: NotificationViewModel? = null
) { ... }
```

### 3. Implement Realtime Reconnection with Backoff
Add automatic reconnection logic for realtime subscriptions with exponential backoff. Consider using a HealthCheck worker that periodically verifies realtime connection and reconnects if needed.

### 4. Standardize Sync Operation Types
Choose one of:
- Option A: Always use "create", "update", "delete", "upsert" consistently
- Option B: Have processReaction/processRating check operation type for consistency

### 5. Add Permission Request UI Flow
Enhance MainActivity with a proper permission request flow:
```kotlin
// Check and request all required permissions on first launch
val requiredPermissions = mutableListOf(Manifest.permission.POST_NOTIFICATIONS)
val missingPermissions = requiredPermissions.filter {
    ActivityCompat.checkSelfPermission(this, it) != PackageManager.PERMISSION_GRANTED
}
if (missingPermissions.isNotEmpty()) {
    ActivityCompat.requestPermissions(this, missingPermissions.toTypedArray(), CODE)
}
```

### 6. Initialize Notification Infrastructure Earlier
Call `NotificationManager.createNotificationChannels()` in MainApplication or MainActivity.onCreate() before any notifications can be sent.
