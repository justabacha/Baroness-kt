Current State of the Notification System - Baroness-kt
This report details the current implementation status of both in-app and push notification systems within the Baroness-kt codebase.
1. In-App Notifications
   •
   Injection: NotificationViewModel is properly injected into the WishlistRepository.
   ◦
   Logic: In MainActivity.kt, the repository's singleton instance is updated with the NotificationViewModel using WishlistRepository.getInstance(context).setNotificationViewModel(notificationViewModel) (MainActivity.kt:60).
   •
   Triggers: notificationViewModel.showInAppNotification() is correctly called when a wish is inserted via Supabase Realtime.
   ◦
   Condition: It only triggers if the creatorId of the new wish does not match the currentPersonaId of the local user.
   ◦
   Code Path: app/src/main/java/com/baroness/app/repository/WishlistRepository.kt lines 330-338 within the handleWishChange function.
2. Push Notifications (FCM)
   •
   Manifest Registration: FCMService is correctly registered under the .services package.
   ◦
   Location: app/src/AndroidManifest.xml line 76.
   •
   Token Management:
   ◦
   Saving Token: onNewToken() in FCMService.kt (lines 31-45) correctly saves the token to local storage and attempts to sync it to Supabase via ProfileManager.updateFcmToken().
   ◦
   Initialization: The FCM token is also explicitly retrieved and synced upon app launch in MainApplication.kt within the registerFcmToken() method (lines 25-54).
   •
   Notification Channels: Channels are properly initialized.
   ◦
   Initialization: notificationManager.createNotificationChannels() is called in MainApplication.kt line 22.
   ◦
   Implementation: The channels (wishlist_notifications, messages_notifications, etc.) are defined in NotificationManager.kt.
3. Supabase Side
   •
   Kotlin Implementation: ProfileManager.updateFcmToken() is fully implemented and correctly patches the fcm_token column in the profiles table (ProfileManager.kt:25).
   •
   Missing Server Components: While the notify-trigger Edge Function is referenced in FEATURE_notification.md, there is no implementation of the Edge Function or the required PostgreSQL database triggers within the codebase or schema files.
4. Runtime Permissions
   •
   Missing Implementation: The POST_NOTIFICATIONS permission (required for Android 13+) is declared in the manifest (AndroidManifest.xml:28) but is NOT requested at runtime anywhere in MainActivity.kt or the navigation flow. Push notifications will be blocked by the system until this is addressed.
5. Missing Pieces
   •
   The Single Missing Piece (Critical): The Supabase Database Trigger.
   ◦
   Even though the app is ready to receive tokens and handle messages, there is currently no logic on the Supabase side to detect a new wish (INSERT on wishlist_items) and automatically invoke an Edge Function to send the FCM payload to the recipient.
   ◦
   Secondary blocker: Missing runtime permission request in MainActivity.kt.
   Verdict
   The In-App Notification system is fully functional (it relies on Realtime, which is implemented). The Push Notification system is partially implemented (client-side infrastructure is ready, but server-side triggers and runtime permissions are missing).
