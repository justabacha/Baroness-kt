## Summary

The codebase generally follows the documented architecture with proper layer separation (screens, viewmodels, repositories, data). The offline-first and realtime philosophies are well-implemented with Room database caching and Supabase realtime subscriptions. However, there are significant discrepancies between the documented design system and actual implementation, particularly in color definitions. The design system documentation appears outdated compared to the actual codebase implementation.

## Critical Issues (Fix Immediately)

### Issue #1: Design System Color Mismatch - Primary Color
- **File(s):** `app/src/main/java/com/baroness/app/ui/theme/Color.kt`, `docs/DESIGN_SYSTEM.md`
- **Problem:** DESIGN_SYSTEM.md specifies Primary color as `#FF6B6B` (coral), but Color.kt does not define this color. Instead, the app uses a different color scheme with `Colors.accent = #FF66CC99` (green) and various purple/pink accent colors.
- **Severity:** 🔴 Critical
- **Suggested Fix:** Update DESIGN_SYSTEM.md to reflect actual colors in use, OR update Color.kt to match documented colors. Current actual colors in Color.kt:
  - `Colors.bg = #FF0A0A0A` (vs documented `#FF121212`)
  - `Colors.accent = #FF66CC99` (green - not documented)
  - `Colors.purpleAccent = #FFAA66FF` (not documented)
  - `Colors.greenAccent = #FF66CC99` (not documented)
  - `Colors.textDim = #FFCCCCCC` (vs documented `#FFB3B3B3`)
  - `Colors.pinkAccent = #FFFF66CC` (not documented)
- **Behaviour Impact:** Major - Inconsistent branding and visual identity
- **Offline Impact:** None

### Issue #2: Design System Color Mismatch - Background and Surface
- **File(s):** `app/src/main/java/com/baroness/app/ui/theme/Theme.kt`, `docs/DESIGN_SYSTEM.md`
- **Problem:** DESIGN_SYSTEM.md specifies Background as `#121212` and Surface as `#1E1E1E`. Theme.kt uses these values in DarkColorScheme, but Color.kt defines `Colors.bg = #FF0A0A0A` which is darker than documented. Screens use `Colors.bg` directly, creating inconsistency.
- **Severity:** 🔴 Critical
- **Suggested Fix:** Standardize background color across Color.kt and Theme.kt. Either:
  1. Update Color.kt `Colors.bg` to `#FF121212` to match DESIGN_SYSTEM.md
  2. Update DESIGN_SYSTEM.md to reflect actual `#FF0A0A0A` in use
- **Behaviour Impact:** Major - Inconsistent visual appearance
- **Offline Impact:** None

### Issue #3: Missing WorkManager for Background Sync
- **File(s):** `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt`
- **Problem:** ARCHITECTURE.md states "Use WorkManager for background sync" but the codebase does not use WorkManager. SyncManager is called directly from repository methods without WorkManager scheduling.
- **Severity:** 🔴 Critical
- **Suggested Fix:** Implement WorkManager to schedule sync operations, especially for:
  - Pending sync queue items
  - Periodic data refresh
  - Retry failed sync operations
- **Behaviour Impact:** Major - Sync may not occur reliably when app is in background or killed
- **Offline Impact:** High - Background sync is critical for offline-first architecture

## Medium Issues (Fix Next)

### Issue #4: State Collection Method Inconsistency
- **File(s):** `app/src/main/java/com/baroness/app/screens/DashboardScreen.kt`, `app/src/main/java/com/baroness/app/screens/PhotosScreen.kt`
- **Problem:** ARCHITECTURE.md specifies "Collect in UI with `collectAsStateWithLifecycle()`" but screens use `collectAsState()` instead, which doesn't automatically handle lifecycle awareness.
- **Severity:** 🟡 Medium
- **Suggested Fix:** Replace `collectAsState()` with `collectAsStateWithLifecycle()` in all screens for proper lifecycle-aware collection.
- **Behaviour Impact:** Minor - May cause unnecessary recompositions when app is in background
- **Offline Impact:** None

### Issue #5: Typography Not Following Design System
- **File(s):** `app/src/main/java/com/baroness/app/ui/theme/Type.kt`, `docs/DESIGN_SYSTEM.md`
- **Problem:** DESIGN_SYSTEM.md specifies:
  - Headlines: 24sp, Bold
  - Body: 16sp, Regular
  - Captions: 12sp, Regular
  Type.kt only defines `bodyLarge = 16sp` and has other styles commented out. Screens use hardcoded font sizes (e.g., DashboardScreen uses dynamic sizing with clamp()).
- **Severity:** 🟡 Medium
- **Suggested Fix:** 
  1. Uncomment and configure all typography styles in Type.kt to match DESIGN_SYSTEM.md
  2. Use MaterialTheme.typography instead of hardcoded font sizes in screens
- **Behaviour Impact:** Minor - Inconsistent typography across app
- **Offline Impact:** None

## Architecture Recommendations

1. **Update Design System Documentation:** The DESIGN_SYSTEM.md file is significantly outdated compared to actual implementation. Either update the code to match the documented design system, or update the documentation to reflect the actual design system in use (green/purple accent colors, darker background, dynamic spacing).

2. **Implement WorkManager:** To fully comply with the offline-first architecture documented in ARCHITECTURE.md, implement WorkManager for background sync operations. This will ensure sync happens reliably even when the app is not actively running.

3. **Standardize Typography:** Create a comprehensive typography system in Type.kt that matches the design system and use MaterialTheme.typography throughout the app instead of hardcoded font sizes.

4. **Create Design Tokens:** Consider creating a centralized design tokens file for spacing, corner radius, and other design values to ensure consistency across the app.

5. **Lifecycle-Aware State Collection:** Migrate all `collectAsState()` calls to `collectAsStateWithLifecycle()` for better performance and resource management.
