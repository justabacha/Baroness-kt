## Summary
The Wishlist feature correctly implements an offline-first foundation using Room and a SyncQueue. However, it lacks robust conflict resolution and reliable background synchronization. The current "pull" logic (Realtime) ignores remote timestamps, leading to potential data loss if local changes are overwritten by stale remote updates. Additionally, several architectural violations (hardcoded colors) were found in the UI layer.

---

## Critical Issues (Fix Immediately)

### Issue #1: Missing Timestamp-based Conflict Resolution
- **File(s):** `WishlistRepository.kt`, `WishDao.kt`
- **Problem:** Incoming remote changes via Realtime or Initial Sync use `OnConflictStrategy.REPLACE` without comparing timestamps. Local pending changes are overwritten by remote data regardless of which is newer.
- **Severity:** 🔴 Critical
- **Suggested Fix:** Add `updatedAt` to `WishEntity`. In `WishDao`, check if `incoming.updatedAt > local.updatedAt` before inserting.
- **Behaviour Impact:** Major
- **Offline Impact:** Causes local offline edits to be lost if a remote update arrives before the local one is synced.

### Issue #2: Incorrect Timestamp Mapping
- **File(s):** `WishlistRepository.kt`
- **Problem:** Realtime updates and Initial Sync use `System.currentTimeMillis()` for `createdAt` instead of the actual remote timestamp from Supabase.
- **Severity:** 🔴 Critical
- **Suggested Fix:** Parse `created_at` and `updated_at` from `WishDto` (ISO string) into Long before saving to Room.
- **Behaviour Impact:** Minor (breaks sorting)
- **Offline Impact:** Makes timestamp-based conflict resolution impossible.

### Issue #3: Race Condition in ID Swapping
- **File(s):** `SyncManager.kt`, `WishlistRepository.kt`
- **Problem:** If a remote update for a newly created wish arrives via Realtime before the local `SyncManager` completes the `tempId -> serverId` swap, Room will have two records for the same wish, and the swap will fail due to PK constraint.
- **Severity:** 🔴 Critical
- **Suggested Fix:** Handle `SQLiteConstraintException` in `SyncManager` by merging the temp record into the existing server record.
- **Behaviour Impact:** Major
- **Offline Impact:** Can stall the sync queue for specific items.

### Issue #4: Missing Periodic Background Sync
- **File(s):** `WishlistRepository.kt`
- **Problem:** Only `OneTimeWorkRequest` is used. Pending items in `SyncQueue` are not synced if the app is closed before the network is restored.
- **Severity:** 🔴 Critical
- **Suggested Fix:** Register a `PeriodicWorkRequest` in `WishlistRepository` or `MainApplication` to periodically flush the `SyncQueue`.
- **Behaviour Impact:** Major
- **Offline Impact:** Prevents eventual consistency for offline changes.
