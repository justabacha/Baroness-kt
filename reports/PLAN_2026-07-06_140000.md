## Issue #1: WorkManager Integration Not Implemented

### Current State
- `app/build.gradle.kts` has no WorkManager dependency
- No `SyncWorker.kt` file exists in the codebase
- `WishlistRepository.kt` calls `syncNow()` directly after every CRUD operation (lines 399, 408, 419, 431, 443)
- `syncNow()` method (lines 446-451) directly calls `syncManager.processQueue()` on the calling thread
- Sync only occurs when app is active and user performs actions
- No background sync when network becomes available after being offline
- Pending changes in SyncQueue may never sync if app is not opened

### Proposed Change
1. Add WorkManager dependency to `app/build.gradle.kts`
2. Create new file `app/src/main/java/com/baroness/app/workers/SyncWorker.kt`
3. Modify `WishlistRepository.kt` to enqueue WorkManager jobs instead of direct sync calls

### Why This Approach
- **Complies with ARCHITECTURE.md line 54:** "WorkManager integration for scheduled/reliable background sync is **planned but not yet implemented**"
- **Complies with docs/specs/Wishlist.md line 91:** "If online, queue sync → SyncManager → WorkManager"
- **Preserves offline-first behavior:** Local Room operations still happen immediately, sync is queued for background
- **No behavior change:** User experience remains the same, sync becomes more reliable
- **Follows AGENT_RULES.md:** Does not remove offline-first behavior, does not replace Room

### Risks
- **Low risk:** WorkManager is a stable Android Jetpack library
- **Testing needed:** Verify that sync jobs execute correctly when network becomes available
- **Edge case:** Ensure that duplicate sync jobs are not enqueued for the same operation
- **Migration:** Existing pending sync queue items will be processed by new SyncWorker

### Files to Touch
- `app/build.gradle.kts` — Add WorkManager dependency after line 100:

- `app/src/main/java/com/baroness/app/workers/SyncWorker.kt` — Create new file:
  ```kotlin
  package com.baroness.app.workers
  
  import android.content.Context
  import androidx.hilt.work.HiltWorker
  import androidx.work.CoroutineWorker
  import androidx.work.WorkerParameters
  import com.baroness.app.utils.SyncManager
  import dagger.assisted.Assisted
  import dagger.assisted.AssistedInject
  
  class SyncWorker @AssistedInject constructor(
      @Assisted private val context: Context,
      @Assisted workerParams: WorkerParameters,
      private val syncManager: SyncManager
  ) : CoroutineWorker(context, workerParams) {
      
      override suspend fun doWork(): Result {
          return try {
              syncManager.processQueue()
              Result.success()
          } catch (e: Exception) {
              Result.retry()
          }
      }
  }
  ```

- `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt` — Modify:
  - Add import: `import androidx.work.*`
  - Add WorkManager instance: `private val workManager = WorkManager.getInstance(context)`
  - Replace `syncNow()` method (lines 446-451) with:
  ```kotlin
  suspend fun syncNow() {
      Log.d(TAG, "Enqueuing sync work")
      val workRequest = OneTimeWorkRequestBuilder<SyncWorker>()
          .setConstraints(
              Constraints.Builder()
                  .setRequiredNetworkType(NetworkType.CONNECTED)
                  .build()
          )
          .setBackoffCriteria(
              BackoffPolicy.LINEAR,
              30,
              TimeUnit.SECONDS
          )
          .build()
      workManager.enqueue(workRequest)
  }
  ```
  - Add import: `import java.util.concurrent.TimeUnit`

## Issue #2: State Collection Method Violates Architecture Guidelines

### Current State
- `WishlistScreen.kt` lines 35-50 use `collectAsState()` for all 16 StateFlow collections
- No import for `collectAsStateWithLifecycle`
- State continues to be collected when app is in background
- Unnecessary recompositions waste CPU and battery
- Potential memory leaks if flows are not properly cancelled

### Proposed Change
1. Add import for `collectAsStateWithLifecycle` to `WishlistScreen.kt`
2. Replace all 16 `collectAsState()` calls with `collectAsStateWithLifecycle()`

### Why This Approach
- **Complies with ARCHITECTURE.md line 40:** "Collect in UI with `collectAsStateWithLifecycle()`"
- **Preserves existing behavior:** UI behavior remains identical, just more efficient
- **No API changes:** StateFlow types remain the same, only collection method changes
- **Follows AGENT_RULES.md:** Preserves existing behavior, no refactoring of unrelated code
- **Low complexity:** Simple string replacement across 16 lines

### Risks
- **Very low risk:** `collectAsStateWithLifecycle()` is a drop-in replacement for `collectAsState()`
- **Testing needed:** Verify that state still updates correctly when screen is resumed
- **No breaking changes:** The API is backward compatible
