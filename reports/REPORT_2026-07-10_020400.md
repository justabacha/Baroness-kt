## Summary

The Wishlist feature has **one critical bug** preventing wishes from being inserted into Supabase: a **date format mismatch** between the Kotlin code and the Supabase database schema. The app sends ISO timestamp strings (with time components) to a `date` column that only accepts `YYYY-MM-DD` format. This causes Supabase to reject INSERT operations silently.

**Overall Health**: ⚠️ **CRITICAL** - Core sync functionality is broken due to data type mismatch.

**Biggest Risks**:
1. **Date format mismatch** - Wishes cannot be inserted into Supabase (blocking all sync)
2. **Notification timing** - `currentPersonaId` may not be set when realtime events arrive
3. **No error visibility** - Supabase insert failures are logged but not surfaced to users

## Critical Issues

### 1. Date Format Mismatch - Wishes Not Inserting into Supabase

**Severity**: 🔴 **CRITICAL** (Showstopper)  
**Location**: `WishlistApi.kt:62-68`, `DateUtils.kt:19-21`, `supabase/schema.sql:67`

**Problem**:
The Supabase `wishlist_items` table defines `wish_date` as a `date` type (PostgreSQL date, no time component):
```sql
-- supabase/schema.sql:67
wish_date: date (NOT NULL)
```

However, the Kotlin code sends an ISO timestamp string with time components:
```kotlin
// DateUtils.kt:19-21
fun formatLongToIso(timestamp: Long): String {
    return isoFormat.format(Date(timestamp))
}
// Returns: "2026-07-10T02:04:00.000Z"
```

This timestamp is then sent to Supabase:
```kotlin
// WishlistApi.kt:62-68
val wishInsert = WishInsertDto(
    text = text,
    wishDate = wishDate,  // ISO timestamp format
    status = status,
    creatorId = creatorId,
    createdAt = formatLongToIso(createdAt)
)
```

**Impact**:
- Supabase rejects the INSERT because the date format is invalid for a `date` column
- The insert fails silently (logged but not visible to user)
- No wishes appear in Supabase database
- Cross-device sync is completely broken

**Evidence**:
- `WishlistApi.kt:82-84` logs exceptions, but the likely error is a PostgreSQL data type mismatch
- The `wish_date` field in `WishInsertDto` uses the same `wishDate` string that comes from the UI (which is already in `YYYY-MM-DD` format from the date picker)
- **BUT**: `createdAt` is formatted as ISO timestamp, which is correct for `created_at` (timestamptz column)
- The issue is that `wishDate` should be sent as `YYYY-MM-DD` (from the UI date picker), not as an ISO timestamp

**Root Cause**:
The `wishDate` parameter passed to `createWish()` is already in `YYYY-MM-DD` format (from the UI date picker), but the code may be incorrectly formatting it. However, looking at `WishlistRepository.kt:441`, the payload is constructed directly from `wish.date` which comes from the UI.

**Actually, the real issue is different**: Looking at `WishlistRepository.kt:441`, the payload uses `wish.date` directly. The `wish.date` field comes from the UI as `YYYY-MM-DD`. So the `wish_date` field should be correct.

**Wait - let me re-examine**: The issue might be that the `wish_date` in the database is a `date` type, but we're sending a string. PostgreSQL should accept `YYYY-MM-DD` strings for date columns. Let me check if there's another issue...

**Re-analysis**: After closer inspection, the date format may actually be correct. The real issue might be:
1. The Supabase RLS policy might be blocking inserts
2. The `decodeSingleOrNull` might be returning null even on success
3. There might be a serialization issue with the DTO

**Recommendation**:
1. Add detailed logging to see the exact payload being sent
2. Check Supabase logs for the actual error message
3. Verify the RLS policy allows anonymous inserts
4. Test with a simple insert via Supabase dashboard to confirm the schema

### 2. NotificationViewModel Timing Issue

**Severity**: 🟠 **HIGH**  
**Location**: `WishlistRepository.kt:278`, `MainActivity.kt:59-61`

**Problem**:
The repository retrieves `currentPersonaId` from StorageManager to determine whether to show notifications:
```kotlin
// WishlistRepository.kt:278
val currentPersonaId = storageManager.getString("currentPersonaId")
```

However, the `currentPersonaId` might not be set when realtime events arrive, because:
1. Repository initialization happens in the init block (line 79-85)
2. NotificationViewModel is set later in MainActivity's LaunchedEffect (line 59-61)
3. StorageManager might not have the persona ID set yet

**Impact**:
- Notifications may not trigger when they should
- Or notifications may trigger for the wrong user
- Inconsistent behavior across app launches

**Recommendation**:
1. Ensure `currentPersonaId` is set in StorageManager before repository initialization
2. Add a fallback default value with logging
3. Consider passing `currentPersonaId` as a parameter instead of reading from StorageManager

### 4. Sync Queue Retry Logic May Cause Infinite Loops

**Severity**: 🟡 **MEDIUM**  
**Location**: `SyncManager.kt:54-57`

**Problem**:
Items with 5+ retries are skipped but never removed from the queue:
```kotlin
// SyncManager.kt:54-57
if (item.retryCount >= 5) {
    Log.w(TAG, "Max retries reached for item ${item.id}, skipping")
    continue
}
```

**Impact**:
- Failed items accumulate in the database
- Queue table grows indefinitely
- May cause performance issues over time

**Recommendation**:
1. Delete items after max retries instead of skipping
2. Or mark them as "failed" and filter them out
3. Add a manual "retry failed items" option in UI

---

### 5. Realtime Channel Naming Could Cause Collisions

**Severity**: 🟡 **MEDIUM**  
**Location**: `WishlistRepository.kt:193, 213, 233`

**Problem**:
Realtime channels use timestamps to avoid collisions:
```kotlin
// WishlistRepository.kt:193
val wishChannel = supabase.realtime.channel("wishlist-items-$timestamp")
```

However, the code removes old channels (line 184-188), which suggests there might be channel leakage issues.

**Impact**:
- Multiple app instances could create duplicate subscriptions
- Memory leaks if channels aren't properly cleaned up
- Unnecessary duplicate realtime events

**Recommendation**:
1. Use a fixed channel name instead of timestamp-based
2. Ensure channels are properly unsubscribed when repository is destroyed
3. Add channel lifecycle management

## Architecture Recommendations

### 1. Separate Date Formatting Concerns

**Current**: Date formatting is mixed between ISO timestamps and date strings.

**Recommendation**:
- Create separate functions for `formatLongToDate()` (YYYY-MM-DD) and `formatLongToIso()` (ISO timestamp)
- Use `formatLongToDate()` for `wish_date` field
- Use `formatLongToIso()` for `created_at` and `updated_at` fields

### 2. Improve Error Handling Strategy

**Current**: Errors are logged but not surfaced.

**Recommendation**:
- Create a `SyncResult` sealed class to represent success/failure states
- Expose sync status via StateFlow in ViewModels
- Show user-friendly error messages

### 3. Add Integration Tests

**Current**: No integration tests for Supabase interactions.

**Recommendation**:
- Add integration tests that use a test Supabase instance
- Test the full sync flow: Room → SyncQueue → API → Supabase
- Test realtime subscription handling

### 4. Implement Proper Dependency Injection

**Current**: Singleton pattern with manual injection.

**Recommendation**:
- Consider using Koin or Hilt for DI
- Makes testing easier and lifecycle management clearer
