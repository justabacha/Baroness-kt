## Critical Issues Implementation Plans

### Issue #3: Missing WorkManager for Background Sync

#### Current State
SyncManager is called directly from repository methods (WishlistRepository.kt lines 399, 407, 418, 430, 442) using `syncManager.processQueue()`. This synchronous call only executes when the app is active and the repository method is invoked. The sync queue persists in Room database (SyncQueueItem) with retry logic (max 5 retries), but there is no background scheduling mechanism. If the app is killed or in background, pending sync operations will not execute until the app is opened and a repository method triggers sync.

#### Proposed Change
1. Add WorkManager dependency to `app/build.gradle.kts`
2. Create `SyncWorker.kt` in `app/src/main/java/com/baroness/app/workers/` that calls `SyncManager.processQueue()`
3. Modify `WishlistRepository.kt` to enqueue WorkManager work instead of calling `syncManager.processQueue()` directly
4. Add periodic sync work for data refresh (e.g., every 15-30 minutes)
5. Update `docs/ARCHITECTURE.md` line 52 to reflect WorkManager is now implemented

#### Why This Approach
WorkManager is the Android-recommended solution for guaranteed background execution. It handles constraints (network availability, battery optimization, device idle state) automatically, survives app restarts and device reboots, provides built-in retry logic with exponential backoff, and integrates seamlessly with the existing Room-based sync queue. This approach preserves the current sync queue architecture while adding reliable background execution.

#### Risks
- Duplicate sync operations if both WorkManager and direct calls execute (mitigated by removing direct calls)
- WorkManager constraints may delay sync if network is unavailable (acceptable for offline-first architecture)
- Initial implementation complexity with Worker setup and work enqueuing
- Need to ensure WorkManager is properly initialized in Application class

#### Files to Touch
- `app/build.gradle.kts` — Add WorkManager dependency: `implementation("androidx.work:work-runtime-ktx:2.9.1")`
- `app/src/main/java/com/baroness/app/workers/SyncWorker.kt` — Create new Worker class that calls SyncManager.processQueue()
- `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt` — Replace `syncNow()` calls with WorkManager enqueue (lines 399, 407, 418, 430, 442)
- `app/src/main/java/com/baroness/app/BaronessApplication.kt` (if exists) or create Application class — Initialize WorkManager and enqueue periodic sync work
- `docs/ARCHITECTURE.md` — Update line 52 to reflect WorkManager is implemented

#### Files to NOT Touch
- `app/src/main/java/com/baroness/app/utils/SyncManager.kt` — No changes needed, processQueue() logic remains the same
- `app/src/main/java/com/baroness/app/data/local/database/SyncQueueItem.kt` — No changes needed, entity structure is correct
- `app/src/main/java/com/baroness/app/data/local/dao/SyncQueueDao.kt` — No changes needed, DAO is correct

### Issue #4: State Collection Method Inconsistency

#### Current State
Screens use `collectAsState()` instead of `collectAsStateWithLifecycle()`. DashboardScreen.kt lines 97-104 use `collectAsState()` for 8 different StateFlow collections (userProfile, greeting, currentTime, todayDate, vibe, weather, isInitialLoading, isRefreshing). PhotosScreen.kt line 43-44 uses `collectAsState()` for uiState and selectedPhotoIndex. This doesn't automatically handle lifecycle awareness as specified in ARCHITECTURE.md line 38.

#### Proposed Change
Replace all `collectAsState()` calls with `collectAsStateWithLifecycle()` in screen files. Add the required import `androidx.lifecycle.compose.collectAsStateWithLifecycle` to each affected file.

#### Why This Approach
`collectAsStateWithLifecycle()` automatically stops collection when the view is in the background and resumes when it's in the foreground, preventing unnecessary recompositions and resource usage. This is the recommended pattern per ARCHITECTURE.md and Android best practices. The change is a simple import and function name replacement with no behavior change during active use.

#### Risks
- Minimal risk - this is a direct function replacement with identical API
- Need to ensure import is added correctly
- No behavior change expected, only performance improvement

#### Files to Touch
- `app/src/main/java/com/baroness/app/screens/DashboardScreen.kt` — Replace `collectAsState()` with `collectAsStateWithLifecycle()` on lines 97-104, add import
- `app/src/main/java/com/baroness/app/screens/PhotosScreen.kt` — Replace `collectAsState()` with `collectAsStateWithLifecycle()` on lines 43-44, add import
- Check other screen files (GateScreen.kt, ProfileSetupScreen.kt, WishlistScreen.kt) for similar patterns and fix if found

#### Files to NOT Touch
- `app/src/main/java/com/baroness/app/viewmodels/` — No changes needed, ViewModels emit StateFlow correctly
- `app/src/main/java/com/baroness/app/ui/theme/` — No changes needed, theme files unrelated
- Repository and data layer files — No changes needed, data layer unrelated

### Issue #5: Typography Not Following Design System

#### Current State
Type.kt only has `bodyLarge` configured with other typography styles commented out (lines 18-33). Screens continue using dynamic font sizing with `clamp()` instead of MaterialTheme.typography. DashboardScreen.kt uses dynamic sizing with clamp() for welcomeFont (line 79), greetFont (line 80), timeFont (line 81), and other font sizes. The design system specifies Headlines: 24sp Bold, Body: 16sp Regular, Captions: 12sp Regular but these are not available in MaterialTheme.typography.

#### Proposed Change
1. Uncomment and configure typography styles in Type.kt to match DESIGN_SYSTEM.md specifications:
   - headlineLarge: 24sp, Bold
   - bodyLarge: 16sp, Regular (already configured)
   - labelSmall: 12sp, Regular
2. Add additional useful styles (titleMedium, bodySmall) for comprehensive coverage
3. Update screens to use MaterialTheme.typography where appropriate, but preserve dynamic clamp() sizing for responsive design where it adds value

#### Why This Approach
Providing a comprehensive typography system in Type.kt enables consistent text styling across the app using MaterialTheme.typography. However, the dynamic clamp() sizing in DashboardScreen provides responsive design benefits that should be preserved. The approach balances standardization with the existing responsive design pattern.

#### Risks
- Risk of breaking responsive design if clamp() is removed entirely
- Need to carefully identify where MaterialTheme.typography can be used vs where dynamic sizing is needed
- Typography changes may affect visual appearance across the app

#### Files to Touch
- `app/src/main/java/com/baroness/app/ui/theme/Type.kt` — Uncomment and configure typography styles (lines 18-33), add additional styles
- `app/src/main/java/com/baroness/app/screens/DashboardScreen.kt` — Replace hardcoded font sizes with MaterialTheme.typography where appropriate, preserve clamp() for responsive elements
- Check other screen files (PhotosScreen.kt, WishlistScreen.kt, etc.) for hardcoded font sizes and replace with MaterialTheme.typography where appropriate
