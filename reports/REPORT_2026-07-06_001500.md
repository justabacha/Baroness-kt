## Summary

Investigation of why User B does not see User A's new wish instantly when both have the Wishlist screen open. The client-side realtime subscription implementation is correct and follows Supabase best practices. The UI properly observes StateFlow updates from the local Room database. However, **the root cause is that Supabase RLS policies do not explicitly enable realtime replication for the wishlist tables**. Without realtime publication enabled, Supabase will not broadcast database changes to subscribed clients, regardless of the client-side subscription configuration.

---

## Investigation Findings

### 1. Why doesn't User B see User A's new wish instantly?

**Root Cause:** Supabase RLS policies for wishlist tables (wishlist_items, wishlist_reactions, wishlist_ratings) do not explicitly enable realtime replication. While the policies allow CRUD operations, they do not configure the tables to broadcast changes via realtime. This is a Supabase-specific requirement: tables must be configured for realtime publication to emit events to subscribed clients.

**Expected Flow (not working):**
1. User A creates wish → Repository inserts to local Room → SyncManager queues → API call to Supabase
2. Supabase should broadcast realtime event → WishlistRepository receives via postgresChangeFlow
3. handleWishChange() updates local Room → Room Flow emits → ViewModel StateFlow updates → UI recomposes

**Actual Flow (what happens):**
1. User A creates wish → Repository inserts to local Room → SyncManager queues → API call to Supabase
2. Supabase stores the change but **does not broadcast** (realtime not enabled)
3. User B's client never receives the event → Local Room not updated → UI shows stale data
4. User B only sees the new wish when they manually refresh or the app restarts (triggers initialSync)

### 4. Are RLS policies blocking realtime broadcasts?

**Status:** ❌ BLOCKING REALTIME

**Analysis:**
From `supabase/policies.sql`:

**wishlist_items policies (lines 28-32):**
- SELECT: "wishlist_items_select" (PERMISSIVE, public, qual: true)
- INSERT: "wishlist_items_insert" (PERMISSIVE, public, with_check: true)
- UPDATE: "wishlist_items_update" (PERMISSIVE, public, qual: true)
- DELETE: "wishlist_items_delete" (PERMISSIVE, public, qual: true)

**wishlist_reactions policies (lines 34-38):**
- SELECT: "wishlist_reactions_select" (PERMISSIVE, public, qual: true)
- INSERT: "wishlist_reactions_insert" (PERMISSIVE, public, with_check: true)
- UPDATE: "wishlist_reactions_update" (PERMISSIVE, public, qual: true)
- DELETE: "wishlist_reactions_delete" (PERMISSIVE, public, with_check: true)

**wishlist_ratings policies (lines 40-44):**
- SELECT: "wishlist_ratings_select" (PERMISSIVE, public, qual: true)
- INSERT: "wishlist_ratings_insert" (PERMISSIVE, public, with_check: true)
- UPDATE: "wishlist_ratings_update" (PERMISSIVE, public, qual: true)
- DELETE: "wishlist_ratings_delete" (PERMISSIVE, public, with_check: true)

**Issue:** These policies allow CRUD operations but **do not explicitly enable realtime replication**. In Supabase, tables must be configured for realtime publication separately from RLS policies. The policies shown are standard RLS policies for access control, not realtime publication configuration.

**Required Fix:** Enable realtime replication for the three wishlist tables in Supabase. This is typically done via:
- Supabase Dashboard: Database → Replication → Select tables for realtime
- SQL: `ALTER PUBLICATION supabase_realtime ADD TABLE wishlist_items;` (and similar for reactions, ratings)

## Critical Issues

### Issue #1: Realtime Not Enabled for Wishlist Tables
- **File(s):** supabase/policies.sql (missing configuration), Supabase Dashboard (not configured)
- **Problem:** wishlist_items, wishlist_reactions, and wishlist_ratings tables are not configured for realtime replication in Supabase. RLS policies allow CRUD but do not enable realtime broadcasts.
- **Severity:** 🔴 Critical
- **Impact:** Users cannot see each other's changes in real-time. Multi-user collaboration is broken.
- **Suggested Fix:** Enable realtime replication for the three wishlist tables in Supabase Dashboard or via SQL:
  ```sql
  ALTER PUBLICATION supabase_realtime ADD TABLE wishlist_items;
  ALTER PUBLICATION supabase_realtime ADD TABLE wishlist_reactions;
  ALTER PUBLICATION supabase_realtime ADD TABLE wishlist_ratings;
  ```
- **Verification:** After enabling, test by having two users create wishes simultaneously and verify instant visibility.

### Issue #2: policies.sql Missing Realtime Documentation
- **File(s):** supabase/policies.sql
- **Problem:** The policies.sql file only documents RLS policies but does not document the required realtime publication configuration. This creates confusion about why realtime isn't working.
- **Severity:** 🟡 Medium
- **Impact:** Developers may not realize that realtime requires separate configuration beyond RLS policies.
- **Suggested Fix:** Add a section to policies.sql documenting realtime publication requirements:
  ```sql
  -- Realtime Publication Configuration
  -- Required for realtime subscriptions to work:
  -- ALTER PUBLICATION supabase_realtime ADD TABLE wishlist_items;
  -- ALTER PUBLICATION supabase_realtime ADD TABLE wishlist_reactions;
  -- ALTER PUBLICATION supabase_realtime ADD TABLE wishlist_ratings;
  ```
