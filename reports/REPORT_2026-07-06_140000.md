## Summary

The Wishlist feature has two critical architecture violations:

1. **WorkManager Integration Missing:** The feature spec (docs/specs/Wishlist.md line 91) and ARCHITECTURE.md (line 54) both specify that WorkManager should be used for background sync, but the implementation uses direct synchronous calls to `syncManager.processQueue()` instead. No SyncWorker.kt exists, and no WorkManager dependency is present in build.gradle.kts. This means sync only happens when the app is active and the user performs actions, not in the background when network becomes available.

2. **State Collection Method Incorrect:** WishlistScreen.kt uses `collectAsState()` for all 16 StateFlow collections (lines 35-50), violating ARCHITECTURE.md line 40 which requires `collectAsStateWithLifecycle()`. This causes unnecessary recompositions when the app is in the background and wastes resources.

Both issues are already documented as known issues in the spec (Issue #3 for WorkManager), but the state collection issue is not documented.

## Critical Issues (Fix Immediately)

### Issue #1: WorkManager Integration Not Implemented
- **File(s):** `app/build.gradle.kts`, `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt`
- **Problem:** 
  - **SyncWorker.kt does not exist:** Search returned 0 results
  - **WorkManager dependency missing:** app/build.gradle.kts lines 40-101 contain no WorkManager dependency. Dependencies include Room, Supabase, Coroutines, etc. but no `androidx.work:work-runtime-ktx`
  - **Direct sync calls instead of WorkManager enqueuing:** WishlistRepository.kt calls `syncNow()` directly after every operation:
    - Line 399: `syncNow()` called after `insertWish()`
    - Line 408: `syncNow()` called after `deleteWish()`
    - Line 419: `syncNow()` called after `updateWishStatus()`
    - Line 431: `syncNow()` called after `saveReaction()`
    - Line 443: `syncNow()` called after `saveRating()`
  - The `syncNow()` method (lines 446-451) directly calls `syncManager.processQueue()` without using WorkManager
- **Severity:** 🔴 Critical
- **Evidence:**
  - docs/specs/Wishlist.md line 91: "3. If online, queue sync → SyncManager → WorkManager"
  - docs/specs/Wishlist.md line 103: "Issue #3: Missing WorkManager for background sync (Severity: 🔴)"
  - docs/ARCHITECTURE.md line 52: "Background sync is currently handled by calling SyncManager directly from repository methods"
  - docs/ARCHITECTURE.md line 54: "WorkManager integration for scheduled/reliable background sync is **planned but not yet implemented**"
- **Impact:**
  - Sync only occurs when app is active and user performs actions
  - No background sync when network becomes available after being offline
  - Pending changes in SyncQueue may never sync if app is not opened
  - Violates offline-first philosophy - users expect data to sync automatically
- **Suggested Fix:**
  1. Add WorkManager dependency to app/build.gradle.kts:
     ```kotlin
     implementation("androidx.work:work-runtime-ktx:2.9.0")
     ```
  2. Create SyncWorker.kt that calls SyncManager.processQueue()
  3. Replace direct `syncNow()` calls with WorkManager enqueue calls:
     ```kotlin
     suspend fun syncNow() {
         val workRequest = OneTimeWorkRequestBuilder<SyncWorker>()
             .setConstraints(
                 Constraints.Builder()
                     .setRequiredNetworkType(NetworkType.CONNECTED)
                     .build()
             )
             .build()
         WorkManager.getInstance(context).enqueue(workRequest)
     }
     ```
- **Behaviour Impact:** Critical - Background sync does not work
- **Offline Impact:** Critical - Pending changes may never sync to server

- **Severity:** 🔴 Critical

  ```kotlin
  val wishes by viewModel.wishes.collectAsStateWithLifecycle()

  // ... etc for all 16 collections
  ```
- **Behaviour Impact:** Medium - Performance degradation and battery drain
- **Offline Impact:** None

## Architecture Recommendations

1. **Implement WorkManager for Background Sync:** This is a critical gap in the offline-first architecture. The current implementation only syncs when the app is active and the user performs actions. WorkManager should be used to:
   - Enqueue sync jobs when network-dependent operations fail
   - Retry failed sync operations automatically
   - Sync when network becomes available after being offline
   - Ensure data consistency across devices

2. **Migrate to collectAsStateWithLifecycle():** Replace all `collectAsState()` calls with `collectAsStateWithLifecycle()` across WishlistScreen.kt to comply with ARCHITECTURE.md and improve performance.

3. **Update Documentation:** The state collection issue is not documented in docs/specs/Wishlist.md known issues. Consider adding it as Issue #7.
