## Summary

The Wishlist feature implements a robust offline-first architecture with proper separation of concerns. All write operations correctly write to Room before network operations, ensuring UI responsiveness. The sync pipeline uses WorkManager for background execution, and realtime subscriptions are properly configured. However, there are **critical issues** with the initial sync timing (runs on repository init, not screen open), potential duplicate handling in initial sync, and missing periodic sync for eventual consistency. The architecture is sound but needs refinements for production reliability.

**Overall Health:** 7/10 - Good architecture with critical gaps in sync timing and duplicate prevention.

**Biggest Risks:**
1. Initial sync runs on repository init (singleton) - may not run when screen opens if repository already initialized
2. No duplicate prevention in initial sync - could create duplicate wishes if run multiple times
3. No periodic sync - relies only on realtime and manual sync
4. Missing app resume sync - no reconnection logic for offline-to-online transitions

## Critical Issues

### Issue #1: Initial Sync Timing - Runs on Repository Init, Not Screen Open
- **File(s):** `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt` (lines 79-85)
- **Problem:** `initialSync()` is called in the repository `init` block (line 83). Since `WishlistRepository` is a singleton (lines 87-96), `initialSync()` only runs once when the repository is first instantiated. If the user navigates away from Wishlist and returns later, or if the app is backgrounded and foregrounded, `initialSync()` will not run again. Remote wishes created by another user while the app was backgrounded will not load until app restart.
- **Severity:** 🔴 Critical
- **Impact:** Users may not see remote wishes when returning to the screen, leading to stale data and sync confusion.
- **Current Code:**
  ```kotlin
  init {
      scope.launch {
          fetchProfiles()
          subscribeToRealtime()
          initialSync()  // Only runs once on singleton init
      }
  }
  ```
- **Suggested Fix:** Move `initialSync()` to be called when the Wishlist screen first composes, or add a flag to track when initial sync was last run and re-run if it's been more than X minutes. Alternatively, add a "pull to refresh" or periodic sync mechanism.
- **Offline Impact:** High - Without proper initial sync, users may work with stale data indefinitely if realtime is not enabled or not working.

### Issue #2: Initial Sync Uses Simple Insert - No Duplicate Prevention
- **File(s):** `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt` (lines 133-146)
- **Problem:** `initialSync()` uses `wishDao.upsertWithTimestampCheck()` for wishes (line 144), which is good, but for reactions and ratings it uses simple `insertReaction()` and `insertRating()` (lines 150, 160). If `initialSync()` runs multiple times (e.g., due to the timing issue above), reactions and ratings will be duplicated. Additionally, the `upsertWithTimestampCheck` only compares `updatedAt` - if two devices create wishes with the same timestamp, duplicates could still occur.
- **Severity:** 🔴 Critical
- **Impact:** Duplicate reactions and ratings in the local database, leading to incorrect UI display and potential sync conflicts.
- **Current Code:**
  ```kotlin
  remoteReactions.forEach { dto ->
      reactionDao.insertReaction(ReactionEntity(...))  // No duplicate check
  }
  ```
- **Suggested Fix:** Use upsert (INSERT ... ON CONFLICT REPLACE) for reactions and ratings as well, or add duplicate checking logic. For wishes, consider using a composite check (id + updatedAt) or add a unique constraint.
- **Offline Impact:** Medium - Duplicates are local only, but they confuse users and waste storage.

### Issue #3: Missing Periodic Sync for Eventual Consistency
- **File(s):** `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt` (no periodic sync), `docs/ARCHITECTURE.md` (line 52)
- **Problem:** ARCHITECTURE.md states "Background sync is handled by WorkManager. Both OneTimeWorkRequest (for immediate sync) and PeriodicWorkRequest (for eventual consistency) are implemented." However, the code only implements OneTimeWorkRequest in `syncNow()` (lines 503-518). There is no PeriodicWorkRequest for periodic data refresh. If realtime is not working (which was identified in previous report), there is no mechanism to fetch remote changes periodically.
- **Severity:** 🔴 Critical
- **Impact:** If realtime fails or is not enabled, users will never see remote changes unless they restart the app. This breaks the multi-user collaboration feature.
- **Current Code:** Only OneTimeWorkRequest in `syncNow()`, no periodic work enqueued anywhere.
- **Suggested Fix:** Add PeriodicWorkRequest in the repository init or in an Application class to sync every 15-30 minutes. This provides a fallback if realtime fails.
- **Offline Impact:** High - Without periodic sync, offline-to-online transitions may not fetch remote data.

### Issue #4: No App Resume Sync - Missing Reconnection Logic
- **File(s):** No app resume sync implementation found
- **Problem:** When the app goes from offline to online (e.g., user turns on WiFi, or app is backgrounded and foregrounded with network restored), there is no trigger to sync pending changes or fetch remote updates. The sync queue will only be processed when the user performs a write operation (which calls `syncNow()`). If the user only reads data, pending sync items will never be processed.
- **Severity:** 🔴 Critical
- **Impact:** Pending changes may never sync if the user doesn't perform write operations. Remote changes won't be fetched if realtime is not working.
- **Suggested Fix:** Add a network connectivity listener that triggers sync when the app comes online. Alternatively, add periodic sync as a fallback. Also consider triggering sync when the app resumes from background.
- **Offline Impact:** High - Core offline-first feature is broken without proper reconnection logic.

### Issue #6: Error Handling - No User Notification for Sync Failures
- **File(s):** `app/src/main/java/com/baroness/app/utils/SyncManager.kt` (lines 79-86), `app/src/main/java/com/baroness/app/api/WishlistApi.kt` (lines 82-85, 103-106, 121-124)
- **Problem:** Network failures are logged (which is good) but there is no user notification. If sync fails repeatedly (e.g., due to network issues), the user has no way to know that their changes are not syncing. The sync queue will continue to grow with retry counts, but the user sees no indication of failure.
- **Severity:** 🟡 Medium
- **Impact:** Users may think their changes are synced when they're actually pending locally, leading to data loss if they switch devices.
- **Current Code:** Errors are logged but not surfaced to UI:
  ```kotlin
  } catch (e: Exception) {
      Log.e(TAG, "Create failed with exception: ${e.message}", e)
      null  // Returns null, no user notification
  }
  ```
- **Suggested Fix:** Add a sync status indicator in the UI (e.g., "Syncing...", "Sync failed", "Last synced: 2 min ago"). Consider adding a notification channel for sync failures.
- **Offline Impact:** Medium - Users may not realize their data is at risk.

### Issue #7: WishDao.upsertWithTimestampCheck Uses updatedAt Comparison - Potential Race Condition
- **File(s):** `app/src/main/java/com/baroness/app/data/local/dao/WishDao.kt` (lines 47-53)
- **Problem:** The `upsertWithTimestampCheck` method only compares `updatedAt` to decide whether to insert. If two devices create wishes at the exact same millisecond, or if clocks are slightly out of sync, the check may fail and cause duplicates or missed updates. Additionally, the method doesn't handle the case where `updatedAt` is null or missing.
- **Severity:** 🟡 Medium
- **Impact:** Potential for duplicate wishes or missed updates in edge cases with concurrent edits.
- **Current Code:**
  ```kotlin
  @Transaction
  suspend fun upsertWithTimestampCheck(wish: WishEntity) {
      val existing = getWishById(wish.id)
      if (existing == null || wish.updatedAt > existing.updatedAt) {
          insertWish(wish)
      }
  }
  ```
- **Suggested Fix:** Add null safety for `updatedAt`, consider using a version number or UUID for conflict resolution, or add a "last modified by" field to track which device made the change.
- **Offline Impact:** Low - Edge case, but could cause data inconsistency in concurrent scenarios.

### Issue #8: Realtime Subscription - No Reconnection Logic on Connection Loss
- **File(s):** `app/src/main/java/com/baroness/app/repository/WishlistRepository.kt` (lines 173-259)
- **Problem:** The realtime subscription is set up once in `subscribeToRealtime()` (line 173) with a guard `if (isSubscribed)` (line 174). If the realtime connection drops (e.g., network loss, Supabase restart), there is no reconnection logic. The subscription will remain in a failed state until the app restarts.
- **Severity:** 🟡 Medium
- **Impact:** Realtime updates will stop working until app restart, breaking multi-user collaboration.
- **Current Code:** No reconnection logic, only initial subscription:
  ```kotlin
  private var isSubscribed = false
  private suspend fun subscribeToRealtime() {
      if (isSubscribed) {
          Log.d(TAG, "Already subscribed, skipping")
          return
      }
      // ... subscription logic
      isSubscribed = true
  }
  ```
- **Suggested Fix:** Add a reconnection mechanism that detects connection loss and re-subscribes. Consider using Supabase's built-in reconnection features or implement a heartbeat check.
- **Offline Impact:** Medium - Realtime is a key feature for multi-user collaboration.

## Low Priority / Improvements

### Issue #9: WishlistViewModel Uses Singleton Repository - Potential Memory Leak
- **File(s):** `app/src/main/java/com/baroness/app/viewmodels/WishlistViewModel.kt` (line 17)
- **Problem:** `WishlistViewModel` uses `WishlistRepository.getInstance(context.applicationContext)` (line 17). While the repository is correctly implemented as a singleton, the ViewModel holds a reference to it. Since the repository has a `CoroutineScope(SupervisorJob() + Dispatchers.IO)` (line 64), it may outlive the ViewModel. This is not necessarily a bug, but it's worth noting for lifecycle awareness.
- **Severity:** 🟢 Low
- **Impact:** Minimal - the repository is a singleton and should live for the app lifetime. However, the scope should be tied to the application lifecycle, not the repository.
- **Suggested Fix:** Consider using a lifecycle-aware scope or ensure the repository's scope is properly cancelled when the app terminates. Currently, the scope is never cancelled.
- **Offline Impact:** None - architectural improvement only.

### Issue #10: No Sync Queue Size Limit - Potential Unbounded Growth
- **File(s):** `app/src/main/java/com/baroness/app/utils/SyncManager.kt` (lines 43-89)
- **Problem:** The sync queue can grow unbounded if sync fails repeatedly. While there is a max retry count (5), if the user keeps creating wishes while offline, the queue could accumulate thousands of items. This could cause performance issues and excessive storage usage.
- **Severity:** 🟢 Low
- **Impact:** Low in normal usage, but could be problematic in edge cases (e.g., user creates 1000 wishes offline).
- **Current Code:** No queue size limit, only retry count limit.
- **Suggested Fix:** Add a maximum queue size (e.g., 100 items) and drop oldest items when exceeded. Or add a "sync queue full" notification to the user.
- **Offline Impact:** Low - edge case only.

## Architecture Recommendations

### 1. Fix Initial Sync Timing
Move `initialSync()` from repository init to screen composition or add a "last sync time" check. The repository should track when initial sync was last run and re-run if it's been more than 5-10 minutes. This ensures remote data is fresh when users open the screen.

### 2. Implement Periodic Sync
Add PeriodicWorkRequest to sync every 15-30 minutes as a fallback for realtime. This provides eventual consistency even if realtime fails. Enqueue this in the repository init or in an Application class.

### 3. Add App Resume Sync
Implement a network connectivity listener that triggers sync when the app comes online. This ensures pending changes are synced and remote data is fetched when connectivity is restored.

### 4. Improve Duplicate Prevention
Use upsert for reactions and ratings in initial sync, not simple insert. Add null safety for `updatedAt` comparison. Consider using a version number or UUID for conflict resolution.

### 5. Add Reconnection Logic for Realtime
Implement a heartbeat check or use Supabase's built-in reconnection features to detect connection loss and re-subscribe to realtime channels.

### 6. Add Sync Status UI
Implement a sync status indicator in the UI (e.g., "Syncing...", "Sync failed", "Last synced: 2 min ago"). Add a notification channel for sync failures to alert users when their changes are not syncing.

### 7. Centralize Persona ID Mapping
Create a helper function or enum for the "P"/"B" to "phesty_official"/"baroness_official" mapping to reduce code duplication and improve maintainability.

### 8. Update Documentation
Update ARCHITECTURE.md to reflect the actual implementation (no PeriodicWorkRequest). Add documentation for the sync flow and reconnection logic.

## Overall Verdict
NEEDS FIX

The Wishlist feature has a solid offline-first architecture with proper separation of concerns and correct use of Room, WorkManager, and StateFlow. However, critical gaps in sync timing, duplicate prevention, and reconnection logic make it unsuitable for production use. The architecture is sound but needs refinements for reliability. Once the critical issues are addressed, the feature will be production-ready.

**Priority Order:**
1. Fix initial sync timing (Issue #1)
2. Implement periodic sync (Issue #3)
3. Add app resume sync (Issue #4)
