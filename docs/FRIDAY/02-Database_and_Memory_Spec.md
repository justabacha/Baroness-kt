```bash
supabase gen types typescript --linked > src/types/supabase.ts
```

Environment variables needed (also listed in 03-Backend_Orchestrator_Spec.md §2):

```
SUPABASE_URL=https://<your-project-ref>.supabase.co

```

Use the service role key on the backend only — this system has no per-user RLS model (single/dual-user, not multi-tenant per Philosophy §9), so the backend talks to Supabase with elevated privileges directly.

## 2. Schema Migrations

Run each block below as a separate SQL Editor query, in this exact order (later blocks reference earlier tables via foreign key).

### 2.1 `messages` — Working Memory backing store

```sql
create table messages (
  id uuid primary key default gen_random_uuid(),
  user_id text not null,                 -- app-level user identifier (single or dual-user)
  role text not null check (role in ('user', 'assistant')),
  content text not null,
  session_id uuid not null,              -- groups messages into a conversation session
  is_command boolean not null default false, -- true if classified as command-path
  is_proactive boolean not null default false, -- [FIX 6] true when FRIDAY texted first
  created_at timestamptz not null default now()
);

create index idx_messages_user_created on messages (user_id, created_at desc);
create index idx_messages_session on messages (session_id, created_at asc);
```

**Field notes:**
- `session_id` is generated by the backend session logic (03 §9), not the database. A new session_id is minted whenever the session-gap check (Philosophy §7) determines the previous session has ended.
- `is_command` lets the reflection pass (§4 below) cheaply skip command-path messages, which carry no relationship-relevant content.
- **[FIX 6]** `is_proactive` is `true` only for assistant-role messages generated by the initiative system (Philosophy §7, 03 §9's `checkInitiative`/`generateFollowUpMessage`) — i.e. FRIDAY texting first, unprompted by any user message. It is `false` for every normal conversational or command-acknowledgment reply, including replies that happen to follow up on old topics organically within a user-initiated exchange. This flag is what the `GET /pending-messages` endpoint (03 §10) filters on, so the Android client can distinguish "she texted me" from ordinary reply traffic.

### 2.2 `entities` — Who's Who Tracker

```sql
create table entities (
  id uuid primary key default gen_random_uuid(),
  user_id text not null,
  name text not null,                    -- canonical name, e.g. "Jordan"
  aliases text[] not null default '{}',  -- e.g. ARRAY['Jordy', 'my roommate']
  relationship text,                     -- e.g. "roommate", "sister", "coworker at Acme"
  last_known_fact text,                  -- most recent salient fact, updated on reflection
  entity_type text not null default 'person' check (entity_type in ('person','place','thing')),
  first_mentioned_at timestamptz not null default now(),
  last_updated_at timestamptz not null default now()
);

create unique index idx_entities_user_name on entities (user_id, lower(name));
create index idx_entities_aliases on entities using gin (aliases);
```

**Lookup pattern (used by context builder, 03 §5):** match incoming message text against `name` and `aliases` (case-insensitive substring/array containment), not vector similarity. Entities are looked up, not retrieved semantically — per Philosophy §2.2.

### 2.3 `memories` — Deep Memory store

```sql
create table memories (
  id uuid primary key default gen_random_uuid(),
  user_id text not null,
  content text not null,                 -- the memory itself, written in third-person factual form
  category text not null check (category in (
    'preference',        -- likes/dislikes, standing facts about the user
    'emotional_moment',  -- significant emotional beats worth remembering
    'life_event',        -- concrete events (job interview, trip, milestone)
    'recurring_pattern',  -- observed habits/patterns across sessions
    'entity_link'        -- a fact that connects to an entity (cross-referenced by entity_id)
  )),
  entity_id uuid references entities(id) on delete set null,
  embedding vector(768),                 -- dimension MUST match embedding model output (see note)
  source_session_id uuid,                -- session this memory was extracted from
  created_at timestamptz not null default now()
);

create index idx_memories_user on memories (user_id);
create index idx_memories_category on memories (category);
-- HNSW index for fast approximate nearest-neighbor search
create index idx_memories_embedding on memories
  using hnsw (embedding vector_cosine_ops);
```

**Dimension note:** `vector(768)` assumes a 768-dim embedding model. If the embedding provider used in 03 §4 outputs a different dimension (e.g. 1536), this column definition must match exactly at creation time — pgvector does not allow dimension mismatches at insert time, and altering the column later requires a full table rewrite. Confirm the embedding model's output dimension before running this migration.

### 2.4 `match_memories` — Vector Search Function

```sql
create or replace function match_memories (
  query_embedding vector(768),
  match_user_id text,
  match_threshold float default 0.75,
  match_count int default 5
)
returns table (
  id uuid,
  content text,
  category text,
  entity_id uuid,
  similarity float
)
language sql stable
as $$
  select
    memories.id,
    memories.content,
    memories.category,
    memories.entity_id,
    1 - (memories.embedding <=> query_embedding) as similarity
  from memories
  where memories.user_id = match_user_id
    and 1 - (memories.embedding <=> query_embedding) > match_threshold
  order by memories.embedding <=> query_embedding
  limit match_count;
$$;
```

This function implements the first two steps of the Tea Test (Philosophy §5): cosine similarity search plus a hard threshold cutoff (default 0.75). The third step — topical load-bearing filtering — happens in application code in the context builder (03 §5), not in SQL, because it may require lightweight LLM judgment that doesn't belong in a database function.

**Manual verification step**, run once after creating the function to confirm it executes (returns empty set on an empty table, but confirms no syntax errors):

```sql
select * from match_memories(
  (select embedding from memories limit 1),
  'test-user',
  0.75,
  5
);
```

If `memories` is empty this will return zero rows with no error — that's expected and confirms the function is valid.

## 3. Memory Categories — When To Use Each

The reflection module (§4) must classify each extracted memory into exactly one category. Guidance for correct classification:

| Category | Use when... | Example |
|---|---|---|
| `preference` | The user states or reveals a standing like/dislike/habit that will remain true across many future conversations. | "User dislikes small talk in the morning before coffee." |
| `emotional_moment` | Something emotionally significant happened or was disclosed, independent of whether it recurs. | "User felt anxious the night before their job interview." |
| `life_event` | A concrete, datable event with a beginning/end. | "User had a final-round interview at Acme Corp on March 3rd." |
| `recurring_pattern` | Observed across multiple sessions, not a single data point. | "User tends to message late at night when stressed about work." |
| `entity_link` | The memory is primarily *about* a tracked entity's relationship to the user, and should be cross-referenced. | "User's sister Jordan is going through a divorce." (entity_id → Jordan's row) |

`entity_link` memories should always have `entity_id` populated; all other categories may leave it null unless directly relevant.

## 4. The Reflection System

Reflection is a backend job (implemented in 03-Backend_Orchestrator_Spec.md §9, the "reflection module") that runs after a session ends, per Philosophy §2.4 and §7. This section specifies *what* it stores and *how it's structured* — the orchestration logic lives in doc 03.

### 4.1 Input
All rows from `messages` where `session_id = <ended session>` and `is_command = false`, ordered by `created_at`.

### 4.2 Process (conceptual — exact prompt lives in 03 §9)
1. Send the full session transcript to the reflection LLM call with an instruction to extract: (a) new or updated entity facts, (b) new Deep Memories with categories per §3.
2. Expect a structured JSON response shaped as:

```json
{
  "entities": [
    {
      "name": "Jordan",
      "aliases": ["Jordy"],
      "relationship": "sister",
      "last_known_fact": "Going through a divorce, leaning on user for support."
    }
  ],
  "memories": [
    {
      "content": "User's sister Jordan is going through a divorce; user has been her main support.",
      "category": "entity_link",
      "entity_ref": "Jordan"
    },
    {
      "content": "User felt anxious the night before their Acme Corp interview.",
      "category": "emotional_moment",
      "entity_ref": null
    }
  ]
}
```

3. For each `entities[]` item: upsert into `entities` by `(user_id, lower(name))` — if it exists, update `last_known_fact` and `last_updated_at`, merge new aliases; if not, insert.
4. For each `memories[]` item: resolve `entity_ref` (a name string) to the corresponding `entity_id` from the just-upserted entities (or a prior lookup if the entity already existed and wasn't touched this session). Generate an embedding for `content` (embedding model per 03 §4), and insert into `memories` with `source_session_id` set to the ended session's id.

### 4.3 Storage discipline
- Reflection must not store raw transcript text as a memory. Every stored memory is a distilled, third-person factual statement — not a copy-paste of what was said. This keeps embeddings meaningful and keeps `match_memories` results dense with signal rather than conversational noise.
- If the reflection LLM call fails or returns malformed JSON, the reflection job logs the failure and exits without partial writes (no entity upsert without its corresponding memory writes, and vice versa is fine — but a fully malformed response should write nothing rather than guess). No retry queue is required (Philosophy §9 — no complex failover); a failed reflection simply means that session isn't remembered, which is an acceptable degradation, not a page-worthy incident.
