# Notifications Sector Audit

## 1. Executive Summary

A comprehensive forensic audit of the Notifications subsystem in the Baroness application (`C:\Baroness_Core\Baroness-kt`) was performed across Android Kotlin source files, AndroidManifest declarations, Supabase Edge Functions, database schema triggers, and DataStore persistence layers.

### Key Audit Findings:
1. **Dual Notification Infrastructure**:
   - **System Push & Device Notifications**: FCM token registration via `MainApplication.kt` and `FCMService.kt`, token persistence in DataStore (`"fcm_token"`) synced to Supabase `profiles.fcm_token`, and system notifications posted via `NotificationManager.kt`. Server push notifications are generated by Supabase Edge Function `notify-trigger` and Postgres trigger `012_friday_initiative_notification_trigger.sql`.
   - **In-App Foreground Banners**: An in-app event bus (`NotificationCenter.kt`) delegating to `NotificationViewModel.kt` to expose an animated Compose top banner (`InAppNotification.kt`).
2. **5 Android Notification Channels**:
   - `wishlist_notifications` ("Wishlist", `IMPORTANCE_DEFAULT`)
   - `messages_notifications` ("Messages", `IMPORTANCE_HIGH`)
   - `general_notifications` ("General", `IMPORTANCE_LOW`)
   - `baroness_clock_channel` ("Alarms & Reminders", `IMPORTANCE_HIGH`)
   - `baroness_playback_channel` ("Media Playback", `IMPORTANCE_LOW`)
3. **Android-Owned Channel Authority**: On Android 8.0+ (API 26+), channel properties (sound, vibration, importance, badge, lockscreen visibility) are **Android OS User-Controlled**. The application cannot programmatically alter channel sound or vibration settings after channel creation.
4. **Current Settings Surface State**: `DrawerNotifications.kt` renders static "Coming soon..." text inside a `GlassCategoryBox`. **Zero notification preference keys exist in DataStore or `SettingsViewModel.kt`.**
5. **No Source Modifications**: This task is an audit and investigation only. Zero Kotlin code, Settings UI, notification behavior, or database schemas were modified.

## 2. Notifications Architecture

The application implements two distinct notification channels and lifecycles:

```text
                               NOTIFICATIONS ARCHITECTURE
                               
  SYSTEM PUSH & BACKGROUND PATH                   IN-APP FOREGROUND PATH
  Supabase Event / AlarmReceiver                  In-App Event (e.g. Chat/Sync)
              │                                                │
              ▼                                                ▼
  FCM HTTP v1 API / Local Alarm                        NotificationCenter.show()
              │                                                │
              ▼                                                ▼
  FCMService.onMessageReceived()                      NotificationViewModel
              │                                                │
              ▼                                                ▼
  NotificationManager.showSystemNotification()         currentNotification StateFlow
              │                                                │
              ▼                                                ▼
  Android System Notification Shade                    InAppNotification Compose Banner
  (Posted to target NotificationChannel)               (Animated top overlay, 5s auto-dismiss)
```

### Path 1: System Push & Device Notification Path
- **Token Registration**: On app startup, `MainApplication.kt` and `FCMService.kt` fetch the device token from `FirebaseMessaging.getInstance().token`, store it in DataStore (`"fcm_token"`), and invoke `ProfileManager.updateFcmToken()` to sync the token to Supabase `profiles.fcm_token`.
- **Server Push Dispatch**: When a new wishlist item is inserted or FRIDAY sends a proactive check-in message, Supabase triggers invoke the `notify-trigger` Edge Function. The Edge Function acquires a Google OAuth2 access token and issues an HTTP v1 POST request to `https://fcm.googleapis.com/v1/projects/{projectId}/messages:send`.
- **Client Receipt & Delivery**: `FCMService.onMessageReceived()` parses the incoming `RemoteMessage.data` into a `NotificationData` model and calls `NotificationManager.showSystemNotification()`, which posts a `NotificationCompat` builder object to the target Android `NotificationChannel`.

### Path 2: In-App Foreground Banner Path
- **Event Bus Dispatch**: Application components invoke `NotificationCenter.show(NotificationData)`.
- **Queue Management**: `NotificationCenter` delegates to `NotificationViewModel.kt`, which queues notifications and exposes `currentNotification: StateFlow<NotificationData?>`.
- **UI Rendering**: `MainActivity.kt` observes `currentNotification` and renders `InAppNotification.kt` as an animated top banner with a 5-second auto-dismiss timer or manual tap dismissal.

## 5. Android Notification Channel Audit

The application registers **5 distinct NotificationChannels**:

```text
┌────────────────────────────┬──────────────────────┬─────────────┬──────────────────────┐
│ Channel ID                 │ Channel Name         │ Importance  │ Creation Site        │
├────────────────────────────┼──────────────────────┼─────────────┼──────────────────────┤
│ wishlist_notifications     │ Wishlist             │ DEFAULT (3) │ NotificationManager  │
│ messages_notifications     │ Messages             │ HIGH (4)    │ NotificationManager  │
│ general_notifications      │ General              │ LOW (2)     │ NotificationManager  │
│ baroness_clock_channel     │ Alarms & Reminders   │ HIGH (4)    │ AlarmReceiver        │
│ baroness_playback_channel  │ Media Playback       │ LOW (2)     │ BaronessMediaService │
└────────────────────────────┴──────────────────────┴─────────────┴──────────────────────┘
```

### Android-Owned Channel Authority Rule:
On Android 8.0+ (API 26+), once a `NotificationChannel` is created, its sound, vibration pattern, importance, badge, and lockscreen visibility are **owned by Android OS System Settings**.
- **App Capability**: The app can create channels and assign initial default importance.
- **App Limitation**: The app CANNOT programmatically modify channel importance, override user-selected channel ringtones, or disable channel vibration after creation without deleting and recreating the channel.
- **System Redirection**: The proper Android design pattern to allow users to modify channel properties is launching `Settings.ACTION_CHANNEL_NOTIFICATION_SETTINGS` via an Intent.

## 7. FCM Pipeline

```text
                                FCM TOKEN & PUSH LIFECYCLE
                                
  MainApplication / FCMService              StorageManager                    Supabase profiles Table
  ┌──────────────────────────┐             ┌──────────────┐                  ┌────────────────────────┐
  │ Fetch token via          │────────────>│ Save to      │                  │ Sync token to          │
  │ FirebaseMessaging.token  │             │ "fcm_token"  │─────────────────>│ profiles.fcm_token     │
  └──────────────────────────┘             └──────────────┘                  └────────────────────────┘
                                                                                         │
                                                                                         ▼
  Android System Shade                    FCM Service                      notify-trigger Edge Func
  ┌──────────────────────────┐             ┌──────────────┐                  ┌────────────────────────┐
  │ Display Notification     │<────────────│ Receive      │<─────────────────│ HTTP v1 POST to        │
  │ with deep link intent    │             │ RemoteMessage│                  │ fcm.googleapis.com     │
  └──────────────────────────┘             └──────────────┘                  └────────────────────────┘
```

### Forensic Pipeline Tracing:
1. **Token Acquisition**: `FirebaseMessaging.getInstance().token` in `MainApplication.kt` and `FCMService.onNewToken()`.
2. **Local Persistence**: Stored in `StorageManager` DataStore under key `"fcm_token"`.
3. **Remote Synchronization**: `ProfileManager.updateFcmToken(personaId, token)` issues a PATCH request to Supabase REST `/rest/v1/profiles?id=eq.{personaId}` updating `fcm_token` and `updated_at`.
4. **Server Push Triggering**:
   - `wishlist_items` INSERT triggers `notify-trigger` Edge Function.
   - `friday_messages` proactive INSERT (`is_proactive = true`) triggers Postgres function `trigger_friday_proactive_notification()` which calls `notify-trigger`.
5. **Payload Schema**: `RemoteMessage.data` payload carries `title`, `body`, `avatar_url`, `feature_type`, `route`.
6. **Delivery Execution**: `FCMService.onMessageReceived()` parses payload into `NotificationData` and invokes `NotificationManager.showSystemNotification()`.
7. **Deep Link Navigation**: `NotificationManager.showSystemNotification()` attaches a `PendingIntent` launching `MainActivity` with `putExtra("route", data.route)` (e.g. `"Wishlist"`, `"Friday"`).

## 11. Sound & Haptics Boundary

- **Notification Sound vs Alarm Sound**:
  - System notification sounds (`wishlist_notifications`, `messages_notifications`, `general_notifications`) are governed by Android `NotificationChannel` settings in System Settings.
  - Alarm & Timer sounds (`alarmSoundOption`, `timerChimeOption`) are played directly by `ClockSoundPlayer.kt` using `RingtoneManager` or `ToneGenerator` streams, controlled by `SettingsViewModel`.
- **Notification Vibration vs Alarm Vibration**:
  - System notification vibration is governed by Android `NotificationChannel` settings.
  - Alarm & Timer vibration is executed directly by `ClockSoundPlayer.playVibration(context, patternName)` using `Vibrator` or `VibratorManager`, controlled by `SettingsViewModel`.
- **Boundary Conclusion**: Notification sounds and vibrations are OS/Channel managed and must NOT duplicate `SoundHapticsSettingsPage.kt` controls.

## 12. Privacy Boundary

- **Message Content in Notifications**: FCM payloads and `NotificationCompat` builders include full message body text and title.
- **Lockscreen Previews**: On Android 8.0+, lockscreen notification preview behavior (Show all, Hide sensitive, Don't show) is managed globally or per-channel by Android OS Security & Privacy settings.
- **Vault Gate (`GateScreen.kt`) Interactions**: System notifications posted to Android OS notification shade display content regardless of whether `GateScreen` is locked.
- **Privacy Boundary Rule**: Notification content privacy toggles belong to the **Privacy & Security** domain or Android System Settings.

## 14. Obvious Correctness Issues (Documentation Only)

1. **`FCMService.kt` Foreground Decision Logic**: `FCMService.onMessageReceived()` contains a `// TODO: Logic to decide between System vs In-App notification` comment and currently always invokes `showSystemNotification()`.
2. **Hardcoded Small Icon Resource in Notification Manager**: `NotificationManager.kt` line 48 uses `R.drawable.icon` with comment `// TODO: Use a proper silhouette icon`. On modern Android, non-silhouette notification icons appear as solid white squares on some devices.
3. **Hardcoded Channel ID in Supabase Trigger**: `012_friday_initiative_notification_trigger.sql` hardcodes `wishlist_notifications` or calls `notify-trigger` which hardcodes `channel_id: 'wishlist_notifications'` for FRIDAY proactive messages instead of `general_notifications` or a dedicated FRIDAY channel.
4. **Hardcoded Service Role Token in Postgres Trigger**: `012_friday_initiative_notification_trigger.sql` contains a hardcoded bearer token string in the SQL trigger function definition.
5. **No App-Side Opt-Out Flow for FCM Push**: The server pushes FCM messages whenever `wishlist_items` or proactive `friday_messages` are created; there is no database flag in `profiles` or DataStore to suppress FCM sends server-side.
